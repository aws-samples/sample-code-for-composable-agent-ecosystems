Quality Gates

How Tessera is designed to enforce output quality — hard failures, not silent fallbacks.

Overview Ecosystems Running Builder Tool Catalog Quality Agent Types Quality Gates Files FAQ

Philosophy: No Silent Fallbacks

Tessera's quality system is designed around one principle: fail loudly. When an agent produces invalid output, the run is designed to fail with a clear error message rather than silently continuing with bad data. This helps you know when something went wrong.

Quality gates are enforced strictly: if a gate is violated, the agent output is rejected and the run reports an error rather than continuing with unverified data.

Gate 1: Output Kind Validation

Every agent's output is validated against its output_kind contract immediately after execution. This is the first gate — if it fails, nothing downstream runs.

KindGate Condition (fails if violated)
analyst / synthesizerMust contain ## STRUCTURED FINDINGS section. Empty findings rejected.
challengerMust contain ## VERDICT (STRONG/ADEQUATE/WEAK) + ## WEAKNESSES. Verdict-consistency: any BLOCKER weakness → verdict must be WEAK.
reporterProse ≥200 characters. Must NOT contain STRUCTURED FINDINGS section.
drafterMust contain ## SUMMARY header. Total output ≥100 characters.
creativeOutput ≥50 characters.
operatorMust contain ## RESULT with status: SUCCESS / FAILURE / DRY_RUN / AWAITING_APPROVAL.
chatAny non-empty response.
If your agent keeps failing kind validation, check its system prompt. The prompt must instruct the agent to produce the required sections for its kind.

Gate 2: Output Format Validation

After kind validation passes, agents with a declared output_format (json, yaml, html, csv) go through format validation:

FormatGate Condition
jsonMust contain a fenced ```json ... ``` block that parses as valid JSON
yamlMust contain a fenced ```yaml ... ``` block that parses as valid YAML
htmlMust contain a fenced ```html ... ``` block (or inline <html>...</html>) with proper open/close tags
csvMust contain a fenced ```csv ... ``` block with ≥1 header row + ≥1 data row

Exception: If the agent has code_interpreter in its tools and save_as is declared, format validation is skipped — the artifact is expected to be produced programmatically via code.

Gate 3: Citation Validation

Synthesizer agents (those with depends_on) must cite their upstream agents. This prevents synthesizers from ignoring upstream work and generating standalone claims.

Rules

  • Each upstream agent in depends_on must be cited at least once using [per agent_id: ...] markers
  • The threshold is configurable per ecosystem (default: 1 citation per upstream)
  • Escape hatch: claims tagged [novel — reason] are exempt (for genuinely new insights not derived from upstream)

What triggers failure

A synthesizer that produces findings without citing required upstream agents fails with:

Citation validation failed: synthesizer did not cite required upstream agent(s):
  quant_analyst (found 0, need 1), macro_analyst (found 0, need 1).
  Each upstream must appear as `[per <agent_id>: <finding>]` at least 1 time(s).
This gate verifies that synthesizers build on upstream work rather than hallucinating standalone analysis. If a synthesizer has a genuinely novel insight, it should tag it [novel — derived from cross-referencing X and Y].

Gate 4: Internal Grounding (guardrails for Amazon Bedrock)

After an agent completes, its STRUCTURED FINDINGS are checked against available evidence using Amazon Bedrock Guardrails contextual-grounding:

Grounding Source (what claims are checked against)

  • Upstream agent outputs — all agents that ran before this one
  • This agent's own tool-call results — the actual data returned by web_search, http_request, etc.

How it works

  1. STRUCTURED FINDINGS are extracted (claim-dense text)
  2. If output exceeds 4,500 chars, it's chunked at paragraph boundaries
  3. Each chunk is sent to Amazon Bedrock guardrails with the grounding source
  4. Amazon Bedrock returns a grounding score and relevance score
  5. Any non-NONE action (BLOCKED, GUARDRAIL_INTERVENED) means grounding failed

What it catches

  • Claims that don't appear in any evidence (hallucinated facts)
  • Numbers that don't match tool results (e.g., "$158B revenue" when the tool returned "$142B")
  • Fabricated source references

What it doesn't catch

  • Claims about the real world that no tool was called to verify (that's what external grounding handles)
  • Logical errors in reasoning (that's what the challenger handles)
If TESSERA_GUARDRAIL_ID is not configured, the grounding check reports a configuration error rather than skipping verification.

Gate 5: External Grounding (Web Verification)

Time-sensitive claims (prices, dates, "recent" events, "current" statistics) are verified against fresh web sources:

Process

  1. Time-sensitive claims are extracted from agent output (regex + LLM extraction)
  2. Each claim is searched via web search
  3. Sonnet 4 evaluator compares the claim against search results
  4. Each claim receives a verdict: verified, unverified, or contradicted
  5. Results are pushed to the UI as per-claim badges

Verdicts

VerdictMeaning
verifiedWeb search results corroborate the claim. Source URL provided.
unverifiedNo evidence found to confirm or deny. The claim may be correct but couldn't be verified.
contradictedWeb search results actively contradict the claim. Source URL provided.
If the web search API key is missing or Amazon Bedrock is unavailable during evaluation, the Lambda reports an error so you know verification could not complete.

Gate 6: Challenger Verdict Consistency

The challenger agent has its own internal consistency gate:

  • If any weakness is tagged as BLOCKER severity, the verdict MUST be WEAK
  • A challenger that finds blockers but still says "STRONG" or "ADEQUATE" fails validation
  • This prevents the challenger from being a rubber stamp

Gate Execution Order

Gates run in sequence. If any gate fails, subsequent gates do not run:

  1. Kind validation — immediately after agent execution
  2. Format validation — if output_format is declared
  3. Citation validation — if agent is a synthesizer
  4. Internal grounding — Step Functions task after the agent
  5. External grounding — Step Functions task after internal grounding
  6. Challenger review — runs after all agents in the ecosystem complete

What Happens When a Gate Fails

  • The agent's status changes to error (red pulsing dot in the UI)
  • A STATE_DELTA event is broadcast with the error message
  • The Step Functions execution may fail (depending on ecosystem error handling)
  • The error message is specific: it tells you which gate failed, what was expected, and what was actually produced
Quality gate errors always include the last 300 characters of the agent's output in the error message, so you can see what went wrong without digging into logs.

Gate Modes & Operator Decisions

Each gate runs in one of three modes (set per gate in the ecosystem YAML, e.g. quality.gates.output_kind):

ModeBehaviour when the gate trips
ask (default)Pauses and asks you to decide — a gate dialogue opens and an item is posted to the Attention inbox.
warnLogs a warning and continues the run.
haltFails the run immediately.

In ask mode the dialogue leads with the reviewer's actual verdict and the specific concern — e.g. "rated ADEQUATE overall but flagged a BLOCKER about X" — instead of a raw rule-violation string. You then choose:

  • ✓ Accept — proceed as-is. Records that the concern is accepted, so later checkpoints don't re-raise the same issue.
  • ↻ Loop with guidance — re-run with corrective guidance you type. Your guidance is injected into the re-run agents as authoritative operator direction. (Loop requires guidance — re-running with none just repeats the same result.)
  • ✕ Abort — stop the run.

You can discuss the verdict in the dialogue before deciding. If you're away, resolve it later from the Attention inbox — but each gate has a pause deadline, after which the run ends cleanly (GateExpired).

Verdict-consistency (challenger): a checkpoint reviewer logs its weaknesses first and derives the verdict last — any open BLOCKER forces WEAK. So "ADEQUATE with an open blocker" can't occur; if a blocker is real the verdict is WEAK, and you decide whether to Loop (fix it) or Accept.

Configuring Quality Gates

In your ecosystem YAML:

quality:
  challenger: true          # inject challenger agent
  grounding: true           # enable internal + external grounding

agents:
  - id: my_synthesizer
    depends_on: [analyst_a, analyst_b]
    output_kind: synthesizer
    role_contract:
      must_cite_upstream: [analyst_a, analyst_b]
      cite_threshold: 1     # minimum citations per upstream
    output_format:
      type: json
      validate: true
      save_as: analysis.json

The Builder UI exposes the top-level quality toggles (challenger, grounding). For fine-grained control over citation thresholds and output formats, edit the YAML directly.

Disabling Gates (Not Recommended)

To disableHowRisk
ChallengerBuilder: uncheck "Challenger agent" / YAML: quality.challenger: falseNo adversarial review of findings
GroundingBuilder: uncheck "Grounding checks" / YAML: quality.grounding: falseHallucinated claims pass unchecked
Citation enforcementRemove role_contract.must_cite_upstream from agent configSynthesizers may ignore upstream work
Format validationSet output_format.validate: falseMalformed artifacts may be saved
Kind validation (Gate 1) cannot be disabled. Every agent must meet its output_kind contract. This is the minimum bar for a functioning ecosystem.
